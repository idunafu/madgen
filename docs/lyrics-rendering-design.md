## 1. 現時点の推奨

①は「F0中央値を渡す」修正ではなく、**実際に使う範囲と加工計画を候補ごとに作り、選択と合成の共通入力にする**。
②は**原音コピーを基本経路に置き、必要な時間変形と移調だけを施す**。
素材の入口・出口と元録音上のつながりを保ち、WORLDを必須の通過点にしない。

| 判断事項 | 推奨案 | 理由・保留事項 |
| --- | --- | --- |
| 使用区間 | 音素注釈、実際の使用範囲、解析用の周辺範囲を分離 | 合成中に別のコアへ切り替わることをなくす |
| F0 | 合成用44.1 kHz波形の発話+周辺で一度解析し、フレーム時刻と有声・無声を保存 | 16 kHz音素認識は維持できる。F0推定器の交換とは分離 |
| 時間変形 | 音素の入口・定常部・出口を含む対応点を計画に保存 | コアだけを取り出して全長へ伸ばす処理をやめる |
| 原音保持 | 無加工・連続区間はそのままコピーし、内部境界のフェードをしない | 元の波形へ戻せる基準を作る |
| 音量 | 音素ごとのRMS均一化を必須から外す。フレーズ・トラック単位のゲインを基本にする | 素材内部の強弱と有声子音の音量を残す |
| 波形加工 | Rubber Bandを第一の比較実装、TD-PSOLAを周期が安定した素材の比較対象とする | 音質の優位性は未測定。時間対応表と連続ピッチの制約がある |
| WORLD | 現行出力を比較基準に残す。将来の代替経路も明示選択・計画記録する | 失敗時に無断で別方式へ変えると、評価した計画と出力が再び食い違う |

RMVPEの追加、Semi-Markov探索、生成的補修は①②の前提にしない。
まず、推定器や探索器を替えなくても起きている不整合を解消する。

## 2. 現行コードと小規模実験から分かったこと

### 2.1 再現した不整合

[検証スクリプト](research/probe_lyrics_render_contract.py)は1秒の合成信号を使うCPUのみの調査用コード。
実録音、GPUモデル、既存DBを使わず、一時WAVは終了時に削除する。
実行環境はNumPy 2.5.3、pyworld 0.3.5、soundfile 0.14.0。

```powershell
uv run --no-sync --offline --cache-dir .uv-cache python docs/research/probe_lyrics_render_contract.py
```

| 確認事項 | 結果 |
| --- | --- |
| 静かな180 Hz部分と、大きな330 Hz部分を含む800 ms区間を400 msへ合わせる | 選択に使うF0は179.92 Hz、音程+長さコストは0。しかし合成が使うコアは329.89 Hz、移調は約-1,049.59 cents、報告伸長率は1.7551 |
| 同じ持続音でピッチ補正を無効にする | `pitch_corrected=False`でも`pyworld.synthesize`が1回呼ばれる |
| 長さもピッチも変えない非持続音経路 | WORLD呼び出しは0回だが、出力は元波形と一致しない。RMSは0.14577から0.12236へ変化。音量処理とフェードが残る |

詳細値は[結果JSON](research/lyrics-render-contract-results.json)に保存。
最初の信号は同じ数式から16 kHzと44.1 kHzで生成している。実際のデコード・リサンプリングの品質比較ではない。
この実験は評価対象の不一致を示すもので、音声素材に対する各方式の音質順位は示さない。

### 2.2 方針決定時に見落とせない現行仕様

- 合成用キャッシュは既に44.1 kHz・モノラル・PCM16へ変換されている。[ffmpeg.py](../src/madgen/ffmpeg.py#L80)
- `--no-pitch-correct --no-lyrics-stretch`でも`_finish`のRMS正規化とフェードがある。最終ミックスにもピーク正規化とPCM16書き出しがある。[synth.py](../src/madgen/synth.py#L236)、[render.py](../src/madgen/render.py#L468)
- 現在の`plan.json`は元素材範囲、使用F0、伸長率を記録するが、実際のコア開始・終了や時間対応表は記録しない。[render.py](../src/madgen/render.py#L416)
- `stretch_ratio`は最低1で、短縮は先頭側の切断として処理される。将来の伸縮率と同じ意味で流用できない。[synth.py](../src/madgen/synth.py#L170)
- 映像は元セグメント開始を基準に選び、音声のコア抽出・伸縮を追跡しない。新しい計画には音声だけでなく元録音時刻への対応も残す。[render.py](../src/madgen/render.py#L299)
- 現行テストは長音の持続・音程等を検証するが、無加工の再接続で原音に戻る条件を検証していない。[test_lyrics.py](../tests/test_lyrics.py#L221)

## 3. ①の提案: 共通の素材情報と加工計画

### 3.1 「原音」と座標系を定義する

無加工一致の基準は、まず**合成用にデコードした波形のサンプル列**とする。
元のMP4等の圧縮ビット列や、ステレオからモノラルへ変換する前の波形との一致は意味しない。
新規キャッシュは44.1 kHz・float32 PCMを推奨する。既存PCM16キャッシュをfloatへ読み直しても量子化前には戻らないため、必要なら元ファイルから別バージョンとして再デコードする。
モノラルを維持するかステレオも保持するかは別の判断であり、初期案は現行どおりモノラル。

区間の開始・終了と目標配置は、サンプル整数の半開区間`[start, end)`で管理する。
境界を一度だけ丸め、隣接ユニット間で同じ境界値を共有する。
F0の時刻は推定器が返した実時刻を保存する。44.1 kHzの5 msは220.5サンプルなので、整数hop=220の累積で置き換えない。

### 3.2 データの役割を分ける

以下は提案上の型名で、既存の型ではない。

| データ | 内容 | 所有する責務 |
| --- | --- | --- |
| `SourceAnalysis` | 音源・デコード版、発話範囲、解析用周辺範囲、F0時刻列、F0、有声マスク、RMS、解析条件 | 素材についての再利用可能な観測値 |
| `PhoneAnnotation` | 文字起こし音素、音響上位候補、注釈境界、元発話と順序、信頼性情報 | 何を発音しているか。使用範囲そのものとは区別 |
| `UnitVariant` | 使用開始・終了、入口・定常部・出口の候補、対応する注釈、必要な音声コンテキスト | 候補として何を実際に使うか |
| `TransformPlan` | variant/analysisのID、出力範囲、source→output対応点、F0/移調曲線、有声マスク、方式・設定、ゲイン、接続範囲 | 選択時に評価し、合成時に実行する計画 |
| `RenderResult` | 計画ID、実出力長、方式版、遅延補償、実現した時間対応の検証結果 | 実行結果。計画変更を隠す場所にはしない |

`render(plan)`は独自に使用範囲を切り直したり、移調判断用F0を測り直したりしない。
バックエンド固有のスペクトル・周期解析は許すが、共通F0や使用範囲を黙って置き換えない。
失敗時に別の切り方・方式を使うなら別計画として評価する。

### 3.3 F0の保存単位

音素ごとの短いクリップではなく、**発話+周辺**を固定条件で解析し、複数音素から参照する。
初回はDIO+StoneMaskを使い、合成波形と同じ44.1 kHzで実行する案を推奨する。
音素認識用16 kHzを変更する必要はない。サンプルレート変更で推定が良くなるとは断定せず、共通の分析条件を定めるための選択とする。

旧DBの中央値から時系列を復元しない。選択で使う候補の発話について段階的に生成・保存してよいが、
新しい方式の候補同士を比較する時は全候補に同じ解析・計画規則を適用する。
発話が重なる場合は、その解析IDとコンテキストに固定する。複数発話を連続処理する必要が出たら、結合範囲の新しい解析を作り、計画段階で参照を確定する。

SQLiteは索引と設定、配列ファイルは密な特徴系列に使う。最初から外部DBや特徴検索サービスを必要としない。
キャッシュキーは音源内容、デコード設定、発話と周辺の範囲、推定器・版、SR、フレーム周期、F0範囲、スキーマ版を含める。
波形加工キャッシュには計画全体とバックエンド版も含める。

過去のローカル調査でも、長い音声からF0を流用する場合と切り出して再推定する場合で差が出ていた。
これは今回再測定した値ではない。保存範囲を固定する理由の補助情報としてのみ扱う。
元の記録: `work/perf-investigation/report.md`「3. ピッチ結果の再利用」。

### 3.4 時間変形を先に決める

使用区間全体を保持し、定常部は**伸縮を多く負担できる領域**として注釈する。定常部以外を捨てる指示にはしない。
入口・出口の候補は、音素境界、周期性、エネルギー、スペクトル変化等から作るが、最初の評価用素材は人手の対応点でもよい。
自動検出の誤りとレンダラーの誤りを同時に比較しない。

```text
source:  入口 |---- 母音の定常部 ----| 出口
                 ↓ 主に伸縮 ↓
target:  入口 |--------- 定常部 ---------| 出口
```

対応点`(source_sample, output_sample)`を単調に並べ、隣接点ごとの比率を計算する。
たとえば入口・出口の長さを各a、b、使用区間全長をL、目標長をDとすると、定常部の比率は
`(D - a - b) / (L - a - b)`。全体比率`D / L`だけでは負担を評価しない。
目標が入口・出口だけの長さより短ければ、その保護条件のままでは実現不可能と判定し、別素材・別の境界・明示的な保護緩和を検討する。
定常部のない素材を強制的に長音化しない。大幅伸長の許容範囲は試聴前に恣意的な定数で固定しない。

音符の終了とクロスフェードのための重なりは別の範囲にする。常に20 ms延長する設計にはしない。
休符へはみ出してよい範囲も接続計画に含める。

### 3.5 F0と移調率の関係

`t`を元素材時刻、`τ = w(t)`を出力時刻、`f_s(t)`を共通解析の有声F0とする。
目標曲線`f_target(τ)`に厳密に合わせる計画の移調率は、有声フレームで
`q(t) = f_target(w(t)) / f_s(t)`。

元の抑揚を一部残す場合は、同じ使用範囲の代表値`f_ref`を使い、
`f_desired(τ) = f_target(τ) × (f_s(w⁻¹(τ)) / f_ref)^(1 - α)`とする案がある。
`α=0`は素材の抑揚を残す、`α=1`は目標曲線に合わせる設定。
一定の音符でも、`α=1`なら素材のF0が揺れる限り移調率は時間変化する。
したがって「単一音符だから固定倍率でよい」とは限らない。

既定のαは音MADとして残したい抑揚と音程精度の選択なので未確定。比較では0と1を分けて聴く。
無声フレームに音符F0を機械的に割り当てず、有声マスクと、バックエンド制御に必要な比率列を区別する。
F0欠損・低信頼箇所は計画に明示し、無断の有声化はしない。

選択はこの同じ計画から、移調centsの分布、定常部と遷移の伸縮率、破壊する境界数等を評価する。
中央値だけ近くても大きな局所移調が必要な候補を見分ける。重みの数値は比較素材を作るまで確定しない。

## 4. ②の提案: 原音を基本とする合成経路

### 4.1 原音保持の意味を二段階に分ける

1. **無加工区間のサンプル一致**: 時間・音程・ゲイン・接続変更がなければ、デコード済み元波形を直接コピーする。
2. **加工区間の発音・質感保持**: 移調や伸縮がある場合、元の入口・出口・息・強弱を残すように加工する。ただし波形のサンプル一致は要求しない。

時間対応表で傾き1にしただけでは、処理エンジンを通った波形が原音と一致するとは限らない。
無声子音等を厳密にコピーする場合はdry区間と加工区間を分け、実際に必要な局所境界でだけ接続する。
周期・非周期のフレームごとに急に切り替えると別の不連続が生じるため、フレーム単位の無条件スイッチにはしない。

### 4.2 経路の選び方

| 条件 | 経路案 |
| --- | --- |
| 変形なし、元録音で連続 | 一つの連続範囲としてコピー。内部の音素境界にフェード・正規化を入れない |
| 長さだけ変更 | 入口・出口を残す時間対応表で、主に定常部を伸縮 |
| 固定倍率の移調と長さ変更 | 一回の波形加工を第一候補とし、同じ計画で評価 |
| 時間変化する移調 | 連続ピッチ対応の波形加工。音符ごとにエンジンを初期化しない |
| 大幅伸長・不安定周期 | 別素材・別の定常部・周期を合わせた反復等を比較。WORLDへ変える場合も計画上で明示 |

元録音の隣接区間をまとめる条件は、音源、使用サンプル境界、出力境界、時間対応、制御曲線が整合すること。
現在の`next_idx`だけでは足りない。まとめる際も計画の使用範囲・時間対応を変えない。
将来の可変長探索に先立ち、現行の単音素候補でも、選択された連続区間を一つのレンダリング範囲として実行する余地がある。
ただしこれだけでは探索前に脱落した連続候補を救えず、全体の接続最適化が完成するわけではない。

異なる素材の接続は、計画で決めた重複範囲にだけフェードを入れる。
相関の強い同一素材と、相関の弱い別素材では適切な窓が違うため、常に同じ20 msの窓を足す方式を避ける。
周期を合わせる必要がある場合、F0だけでなく波形上の周期位置を求める。
無加工の内部境界を除き、クリック除去の必要性は波形と試聴で確認する。

### 4.3 Rubber Bandで確認できた制約

公式APIでは、オフラインの`setKeyFrameMap`で時間対応表を指定できる一方、オフライン処理開始後のピッチ比変更はできない。
リアルタイムモードは時間・ピッチ比を変更できるが、`setKeyFrameMap`は使えない。
R3は明示指定し、実エンジン版を確認する必要がある。[公式Stretcher API](https://breakfastquay.com/rubberband/code-doc/classRubberBand_1_1RubberBandStretcher.html)

CLIの`--pitchmap`もリアルタイムモードに切り替わり、出力長は厳密ではないと説明されている。
「音符ごとにコマンドを呼ぶ」「timemapとpitchmapを同時に渡す」だけで解決したことにしない。
[公式CLI仕様](https://breakfastquay.com/rubberband/usage.txt)

リアルタイムモードの初期パディング、出力遅延、比率変更時刻、末尾の処理が必要。
出力を所定長に切っただけでは内部の発音位置が合っている保証にならない。
[公式組み込みガイド](https://breakfastquay.com/rubberband/integration.html)

以上から、比較する実装は次の三つに絞れる。これはAPI仕様からの設計案であり、音質の実測結果ではない。

| 案 | 利点 | 検証すべき弱点 |
| --- | --- | --- |
| A: R3オフライン、固定ピッチ比+時間対応表 | 一回の加工で時間配置を制御しやすい | 元のF0変動を平坦化する用途やメリスマ全体には不足 |
| B: オフライン時間変形→連続ピッチ変更 | 時間対応とピッチ制御を分離して調査できる | 二回加工の音質差、時間変形後F0の予測誤差、遅延と内部マーカー位置 |
| C: R3リアルタイムで両方を変更 | 一回の加工で可変比率を扱える | 局所時間対応の精度。伸縮出力数と遅延を管理するアダプターが必要 |

**初期比較はAとB、Cは時間精度の検証付きの対抗案**とする。
Bのピッチ処理には`RubberBandLiveShifter`も候補になる。同APIはピッチ専用で、固定長のブロックを同じ長さで出力し、比率を更新できる。
開始遅延は別途補償する。ブロック境界と比率変更の対応は実験で確認する。
[公式LiveShifter API](https://breakfastquay.com/rubberband/code-doc/classRubberBand_1_1RubberBandLiveShifter.html)

Bでは伸縮前のF0を時間対応表で出力時刻へ投影してピッチ制御を作る。
これは加工後の実F0そのものではないため、検証時は別途測定して誤差を記録する。
二段目で再測定して制御を作り直す案を採るなら、それも候補の仮レンダリング段階に含め、選択後だけ計画を変えない。

### 4.4 TD-PSOLAとWORLDの位置付け

Praatのoverlap-addは元波形、周期位置、目標ピッチ、時間変形を使う。
無声部分の扱いも別にあるため、周期の安定した素材で比較する価値がある。
ただしF0推定値だけでは足りず、周期位置と有声・無声の境界を確認する必要がある。
[公式overlap-add説明](https://www.fon.hum.uva.nl/praat/manual/overlap-add.html)、[Manipulationの構成](https://www.fon.hum.uva.nl/praat/manual/Manipulation.html)

最初から独自PSOLAを実装するより、既存実装で素材への適合性を調べる。
比較器の内部解析が共通F0と違う場合は、その条件を明示する。本体採用時には計画を実行できる入力境界が必要。
反復によるブザー感、息、声の不規則性、大幅移調は評価項目とする。

WORLDは現行出力の比較基準として残す。
共通計画を使う改良版を比較する場合は、共有F0に基づいて分析・再合成し、非周期性制限・無声F0補完・音量均一化をそれぞれ独立した実験条件にする。

### 4.5 この環境で使えるもの

- `uv run --no-sync --offline`で既存のNumPy・pyworld・soundfileを使用できた。追加インストールはしていない。
- PATH上に`rubberband`、`praat`の実行ファイルは見つからなかった。システム全体の未導入を断定するものではない。
- プロジェクトのimageio-ffmpeg同梱FFmpeg 7.1には`rubberband`フィルタがあることをhelpで確認した。
  ただし公開されるオプションにR3指定・時間対応表はなく、これをR3の代用としない。
  FFmpeg 7.1の実装も比較参照した。[公式ソース](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n7.1/libavfilter/af_rubberband.c)
- Rubber BandにはC APIとWindows向けビルド手順がある。試作のCLI呼び出しと、本体用のDLLアダプターは分けて考えられる。
  [C API](https://breakfastquay.com/rubberband/code-doc/rubberband-c_8h.html)、[ビルド手順](https://github.com/breakfastquay/rubberband/blob/default/COMPILING.md)
- 同梱する場合は、MITの本体コードとは別に、Rubber BandのGPLまたは商用ライセンスと依存物の配布条件を確認する。
  サブプロセス化だけで条件の確認が不要とは扱わない。[公式ライセンス説明](https://breakfastquay.com/rubberband/license.html)

## 5. 実装を分ける順序

| 段階 | 変更 | 完了条件 |
| --- | --- | --- |
| 1 | デコード座標、解析キャッシュ、`UnitVariant`と`TransformPlan`を用意。選択で使用範囲・F0・変形負担を評価する | 合成が同じ計画を受け取り、使用範囲や移調量を再決定しない。候補の局所計画を検査できる |
| 2 | 無加工コピーと連続範囲の実行を追加。ゲイン・接続処理を独立させる | 元の順序・長さ・ピッチで再構成すると、ミックス前の波形がサンプル一致する |
| 3 | 時間対応表を実行する波形加工アダプターを追加 | 長さ、入口・出口、内部マーカーの位置、遅延補償が計画と一致するかを測定できる |
| 4 | 可変ピッチを扱うA/B/C案とTD-PSOLAを同一素材で比較 | 品質と時間精度を根拠に採用方式を決定する。固定倍率だけの試作で歌唱対応完了としない |
| 5 | 加工後の接続評価と可変長探索へ接続 | 仮レンダリングと最終出力が同じ計画・実装・設定を使う |

現行の辞書式重みを最適解として維持する必要はないが、段階1〜4の比較では候補を固定し、
選択変更と加工変更の寄与を混ぜない。初期の自動選択は簡単なDPでもよく、後から可変長へ拡張できる計画境界を優先する。

## 6. 方針を確定するための比較

### 6.1 比較素材と観測値

素材は長母音、CV/VC遷移、有声子音、無声摩擦音、息・囁き、声の不規則性、短い音符、メリスマを含める。
同じ素材・同じ使用範囲・同じ時間対応・同じ目標曲線で方式を比較する。
可聴比較用のゲイン調整はフレーズ全体へ同じ規則で適用し、計測用の無加工出力とは分ける。

| 実験 | 判定に使うもの |
| --- | --- |
| 無加工の分割・再接続 | デコード済み元波形とのサンプル一致。外側フェード、トラック処理、PCM16化より前に測る |
| 時間だけ0.5/1/2/4倍へ変更 | 目標サンプル数、発音開始と出口、内部マーカー、遷移の明瞭さ。倍率は評価点であり許容範囲の決定ではない |
| ピッチだけ変更 | 0/±3/±12半音、素材F0変動の保持/平坦化、息・子音の変化。測定F0と試聴を併用 |
| 両方・メリスマ | A/B/C・TD-PSOLAで、内部時間精度、音程、継続性、加工感を比較 |
| 元録音上で隣接するCV/VC | 個別合成とまとめた合成で、自然な遷移をどれだけ残せるか |
| 別素材の接続 | クリック、音量段差、位相打ち消し、歌詞の聞き取り。単に滑らかなほど良いとはしない |

原音コピー経路の一致と出力サンプル数は厳密に検証できる。
加工後の発音位置・ピッチの許容誤差は実測と試聴後に決め、最初から任意の閾値を品質保証と呼ばない。
音声評価には計画に使った推定器だけを使わず、必要に応じて独立した推定と聴取を併用する。

### 6.2 今回完了したことと、まだ決めていないこと

完了: 現行実装との照合、14項目の記録、共有計画の初期設計、公式API制約の確認、合成信号での不整合再現、既存環境の機能確認。

未実施: 実録音の比較レンダリング、Rubber Band R3 / LiveShifter / Praatの導入・実行、聴取比較、全コーパス再解析。
したがって、**共通計画・原音コピー・入口出口を残す方針は推奨できるが、加工エンジンの最終採用は保留**。

次の検証では、少数の実録音に人手で使用範囲・入口出口の対応点を付け、まず原音コピー、時間だけ、ピッチだけを比較する。
その結果でA/B/CとTD-PSOLAの採用範囲、抑揚保持の既定値、フォルマント保持の扱いを決める。
